# Spec 작성 규칙

이 파일은 `spec/`와 그 하위 문서에 적용된다.

## 목적

`spec/`는 단순 요구사항 목록이나 구현 계획서가 아니다. 기능이 왜 존재하는지, 누구의 어떤 문제를 해결하는지, 어디까지 지원하는지, 어떤 결정과 제약 위에서 유지되는지를 다음 작업자가 재구성할 수 있도록 하는 장기 기준 문서다.

## 반드시 지킬 규칙

- 문서는 기본적으로 한국어로 작성한다. 코드 식별자와 표준 기술 용어는 원문을 유지할 수 있다.
- 사용자·제품 용어는 [용어사전](./glossary.md)을 따른다. 아마란스와 Jira 같은 최상위 기능 분류는 `서비스`라고 부른다.
- 구현 세부를 제외한 기획, 사용자 경험, 범위, 기술 맥락, 결정 근거, 대안, 리스크, 검증 기준, 변경 이력을 충분히 기록한다.
- 함수 내부 로직, 클래스별 책임 나열, 파일을 따라가는 구현 순서, 번들 산출물 이름처럼 쉽게 낡는 세부는 넣지 않는다.
- 기술 내용은 행동 계약과 의사결정에 영향을 주는 수준으로 기록한다. 예: Manifest V3 권한, DOM 의존성, SPA lifecycle, clipboard 형식, storage 호환성.
- 현재 코드를 읽고 사실을 확인하되, 코드의 우연한 구현을 제품 요구사항으로 승격하지 않는다.
- 사용자 결정이 코드와 충돌하면 사용자 결정을 우선하고 spec·코드·테스트의 정렬 필요성을 명시한다.
- 확정되지 않은 내용은 단정하지 않는다. 가정, 후보, 열린 질문을 구분한다.
- 각 기능 문서에는 상태, 최종 갱신일, 변경 이력이 있어야 한다.
- 변경 이력에는 `무엇이`, `왜` 바뀌었는지 기록한다. 커밋 해시만 남기지 않는다.
- 수용 기준은 사용자가 관찰할 수 있는 결과로 작성한다. 특정 함수 호출이나 내부 변수값을 완료 조건으로 삼지 않는다.
- 비밀, 토큰, 쿠키, 개인 식별 정보, 사내 페이지 본문, 임시 파일 경로를 문서에 남기지 않는다.

## 문서 변경 절차

1. 관련 기능 spec과 [README.md](./README.md)의 문서 체계를 먼저 확인한다.
2. 현재 제품 동작, 테스트, 기존 `docs/plans/` 이력을 근거로 사실과 과거 결정을 구분한다.
3. 사용자에게 보이는 변경이면 목표, 행동 계약, 수용 기준, 리스크, 변경 이력을 함께 갱신한다.
4. 새 기능 문서를 만들면 `spec/README.md`의 문서 목록에 추가한다.
5. 코드 변경이 동반되면 typecheck·test·build 결과 또는 검증하지 못한 이유를 작업 보고에 남긴다.

## 권장 문체

- 결과와 결정부터 쓴다.
- 한 문단에는 하나의 핵심 주장만 둔다.
- 사실, 결정, 추론, 미확정 질문을 섞지 않는다.
- 표는 반복되는 비교나 명확한 계약에만 사용한다.
- 같은 내용을 여러 문서에 복제하지 말고 정본에 쓰고 링크한다.

## 기존 문서와의 관계

`docs/plans/`는 삭제하거나 현재 상태에 맞게 소급 수정하지 않는다. 당시의 조사와 구현 과정을 이해하는 참고 이력으로 보존한다. 현재 계약이 달라졌다면 기능 spec의 변경 이력에서 차이를 설명한다.
