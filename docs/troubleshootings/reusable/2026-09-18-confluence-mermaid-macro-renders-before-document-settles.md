# Mermaid 매크로가 변환 직후에만 엉뚱한 코드블럭을 가리킨다 — 새로고침하면 정상

- 발생일: 2026-09-17 · 확정 2026-09-18
- 원인 위치: **Confluence Mermaid Forge 앱의 렌더 시점** (우리 코드가 아니다)
- 상태: **확정**

## 증상

변환 직후 다이어그램 자리에 오류가 뜬다. 두 가지 모습으로 나온다.

```
Error while loading diagram
No diagram type detected matching given configuration for text: <다른 코드블럭의 내용>
```

```
Error while loading diagram
Code block under with position 2 not found
```

## 결론 — 렌더 시점 문제다. 순번은 맞다

**문서를 그대로 두고 편집기를 새로고침하면 정상으로 그려진다.** 실측으로 확인했다.

```
변환 직후        : Code block under with position 2 not found
새로고침 후 (문서 동일) : flowchart 정상 렌더
```

매크로는 원문을 자기 안에 담지 않고 `guestParams.index` 로 **페이지의 N번째 코드블럭**을 읽는다.
그 조회가 **편집기의 현재 상태가 아니라 아직 가라앉지 않은 문서 상태**를 보는 것으로 보인다.
방금 만들어진 `extension` 과 `expand(원본)` 이 반영되기 전에 iframe 이 먼저 그리면 순번이 다른
블록을 가리키거나 아예 없다고 나온다.

## 잘못 짚었던 길 — 기록해 둔다

오류 문구에 찍힌 본문이 **우리 순번 +1** 자리의 코드블럭과 일치했다. 그 문서에만 있던 특징이
`목록 항목 안의 코드블럭` 하나여서 **"매크로가 목록 안을 세지 않는다"** 고 결론지었다. 목록 안
1개를 빼고 세면 숫자가 정확히 맞아떨어졌다.

**틀렸다.** 그 가설대로 순번을 한 칸 내려 넣었더니 오히려 확실하게 깨졌다 — 매크로가 정말로 한
칸 앞 블록을 읽었다. 즉 **매크로는 목록 안 코드블럭도 센다.** 우리 원래 순번이 맞았다.

### 왜 잘못 짚었나

- 관측은 **하나**(오류 문구의 본문)뿐이었는데 "예측 둘이 맞았다"고 셌다. 두 번째 예측(두 번째
  다이어그램도 깨진다)은 사용자 말에서 가져온 것이고, **깨진 방식을 확인하지 않았다.** 서로 다른
  원인으로도 둘 다 깨질 수 있다.
- **변환 직후의 화면을 문서의 최종 상태와 같다고 가정했다.** 실제로는 그 시점의 매크로 조회가
  가라앉지 않은 상태를 본다.

## 교훈

**비동기로 렌더되는 외부 컴포넌트의 오류 화면을, 문서의 최종 상태에 대한 증거로 쓰지 않는다.**
같은 문서로 새로고침해 보는 것이 첫 번째 확인이어야 했다. 30초면 끝났을 일이다.

숫자가 딱 맞아떨어지는 가설은 설득력이 세지만, **맞아떨어지는 것과 옳은 것은 다르다.** 가설을
세웠으면 그 가설이 **틀렸을 때만 나오는 결과**를 찾아 확인해야 한다. 여기서는 "순번을 바꿔 넣으면
고쳐진다"가 그 확인이었고, 실제로는 더 나빠졌다.

## 대응

우리 순번 계산은 **원래대로** 둔다(문서 전체 코드블럭을 DOM 순서대로 0부터).

변환 결과에 Mermaid 컴포넌트가 생겼으면 **"다이어그램이 오류로 보이면 새로고침하세요"** 를
안내한다. 오류 화면을 그대로 두면 사용자가 변환이 실패했다고 오해한다.
