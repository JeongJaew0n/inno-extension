# troubleshootings

**이슈 관련 기록은 전부 여기 있다.** 만들면서 터진 오류, 사용자가 신고한 현상, 실제로 난 장애,
그리고 그것들을 파고든 분석이 한 폴더에 모인다. 목적은 기록이 아니라 **다시 안 겪는 것**이다.

두 폴더로 나뉘고, 가르는 기준은 하나다.

| 폴더 | 기준 |
|---|---|
| `reusable/` | 원인이 **라이브러리·프레임워크·런타임·OS·외부 서비스**에 있다 |
| `project-specific/` | 원인이 **이 프로젝트의 코드·설정·데이터**에 있다 |

판단이 애매하면 이렇게 자문한다 — **"같은 기술 스택으로 다른 프로젝트를 시작해도
이 글이 쓸모 있나?"** 그렇다면 `reusable/`, 아니면 `project-specific/`.

> **왜 상태로 나누지 않나.** 예전에는 `docs/issue/`(미해결)와 `docs/postmortems/`(해결된 사고)로
> 나눴다. 상태는 시간이 지나면 바뀌어서 문서가 폴더를 옮겨 다녀야 했고, 옮기지 않으면 폴더 이름이
> 거짓말이 됐다. **원인의 위치는 바뀌지 않는다.** 그래서 그쪽을 축으로 쓴다.
> 상태는 문서 머리말의 `상태:` 줄에 적는다.

## 언제 쓰나

- 원인을 찾는 데 **시간이 걸린** 오류 (바로 보이는 오타는 안 적는다)
- 에러 메시지만 보고는 원인을 알 수 없었던 것
- 실제로 무언가 망가졌거나, 판단이 틀렸거나, 뒤늦게 원인을 찾은 일
- 다시 만났을 때 또 헤맬 것 같은 것

**원인을 확정하지 못했어도 적는다.** 관측한 사실과 확인해야 할 것을 남기면 다음 조사가 거기서
시작한다. 상태를 미확정이라고 쓰기만 하면 된다.

## 파일 이름

`YYYY-MM-DD-증상.md`. 증상이 검색되게 짓는다. 나중에 찾는 사람은 원인이 아니라 **증상**으로
찾는다.

```
reusable/2026-09-04-markdown-table-broken-by-blank-lines.md
project-specific/2026-08-26-settings-write-quota-outage.md
```

## 쓰는 규칙

각 폴더의 `README.md`에 템플릿이 있다. 길이는 사안에 따라 다르고, 아래는 어느 길이에서나 지킨다.

- **관찰된 사실과 추정을 반드시 구분한다.** 재현하지 못했으면 못했다고 쓴다. 증거로 뒷받침되지
  않는 부분은 추정이라고 명시한다.
- **사용자가 보고한 원문을 그대로 남긴다.** 요약하면 단서가 사라진다. 실제로 이 폴더에는
  사용자의 한 문장이 원인 판별의 결정적 단서였던 사례가 있다.
- **트리거와 근본 원인을 구분한다.** 방아쇠를 당긴 변경과, 그 변경이 아니었어도 언젠가 터졌을
  구조는 다르다.
- **진단 경로를 남긴다.** 무엇을 먼저 확인했어야 빨랐는지가 다음 조사에서 시간을 아낀다.
- 원인을 사람이 아니라 구조에서 찾는다. 다만 판단 착오가 있었다면 그것도 숨기지 않는다.
- 재발 방지책은 "주의하겠다"가 아니라 **코드·테스트·문서 중 하나**로 남긴다.
- 해결되지 않은 항목은 열린 상태로 남긴다.

> 2026-09-18 이전에 쓴 문서는 폴더 템플릿과 형식이 다르다. **형식을 맞추려고 다시 쓰지 않는다.**
> 당시의 관측과 판단이 그대로 남아 있는 것이 값어치라, 손대면 기록이 아니라 회고가 된다.

## 여기 없는 것

`docs/` 바로 밑의 조사 기록은 **고장 난 것이 없다.** 사전 설계 조사, 동작 방식 조사, 리팩터링
분석이라 이 폴더의 대상이 아니다.
