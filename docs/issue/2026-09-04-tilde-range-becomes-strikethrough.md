# 물결표 범위 표기가 취소선이 된다

- 발생일: 2026-09-04
- 상태: **원인 확정.** 수정 미적용
- 신고 내용: 아래 문장이 취소선이 되어버린다

```text
> 1~3장은 양쪽 코드에서 실제로 확인한 사실이고, 4~5장은 **아직 SE 에 없는 것에 대한 요청 스펙**이므로
```

## 1. 결론

**GFM 취소선 문법에 걸린 것이다.** 확장의 버그가 아니다.

한 문단 안에 물결표가 **2개** 있으면 그 사이가 취소선이 된다. 구분자로 물결표 1개도 인정되기
때문이다.

> **명세와 구현이 다르다.** GFM 명세 본문은 취소선을 "two tildes"로 규정하지만, GitHub 자신의
> 참조 구현(`cmark-gfm`)은 **기본값으로 1개도 허용**한다. 2개만 받으려면 별도 옵션을 켜야 한다.
> 자세한 근거는 5절에 있다.

```text
입력 : 1~3장은 ... 4~5장은
       ^        ^
       여는 구분자   닫는 구분자

출력 : 1<del>3장은 ... 4</del>5장은
```

한국어에서 `1~3`은 범위 표기지만 Markdown에게는 취소선 구분자다. **범위 표기를 두 번 쓰는 순간
걸린다.**

## 2. 실측

변환기에 직접 넣어 확인했다.

| 입력 | 토큰 | 결과 |
| --- | --- | --- |
| `1~3장과 4~5장` | `text del("~3장과 4~") text` | `1<del>3장과 4</del>5장` |
| `1000~2000원` | `text` | `1000~2000원` (그대로) |
| `a~b c~d e~f g~h` | `text del text del text` | 두 쌍 모두 취소선 |
| `~~진짜 취소선~~` | `del("~~진짜 취소선~~")` | 의도한 취소선 |

**물결표가 1개면 아무 일도 없다.** 2개부터 쌍을 이룬다. 4개면 두 쌍이 만들어진다.

신고된 문장을 변환하면 이렇게 된다.

```html
<blockquote><p>1<s>3장은 양쪽 코드에서 실제로 확인한 사실이고, 4</s>5장은 <strong>아직 SE 에 없는 것</strong>이므로</p></blockquote>
```

ADF로는 `strike` 마크 1개가 붙는다.

## 3. 왜 글자도 사라지나

취소선만 생기는 것이 아니라 **물결표 자체가 사라진다.** 구분자로 소비되기 때문이다.

```text
원문 : 1~3장은 ... 4~5장은
텍스트: 13장은 ... 45장은
```

이 세션 초반에 발행된 페이지에서 `13장은 ... 45장은`으로 보이던 것이 이것이다. 당시에는 원인을
따로 규명하지 않고 넘어갔다.

## 4. 우회 방법

문서를 쓰는 쪽에서 셋 중 하나를 쓰면 된다. 모두 실측으로 확인했다.

| 방법 | 입력 | 결과 |
| --- | --- | --- |
| **물결표 앞뒤에 공백** | `1 ~ 3장과 4 ~ 5장` | 그대로 유지 |
| **역슬래시로 escape** | `1\~3장과 4\~5장` | `1~3장과 4~5장` |
| **인라인 코드로 감싸기** | `` `1~3장`과 `4~5장` `` | 그대로 유지 |

공백을 넣으면 GFM의 left-flanking 규칙에 걸려 구분자로 인정되지 않는다. 가장 손이 덜 간다.

물결표 대신 `-`나 `–`를 쓰는 것도 방법이다 (`1-3장`, `1–3장`).

## 5. 명세·구현 확인과 수정 방법

### 5.1 명세 본문은 "two tildes"다

GFM 명세 원문(`cmark-gfm`의 `test/spec.txt`)을 받아 확인했다.

```text
## Strikethrough (extension)

Strikethrough text is any text wrapped in two tildes (`~`).
```

**명세 본문에 단일 물결표는 없다.**

### 5.2 그런데 참조 구현은 기본값으로 1개를 허용한다

`cmark-gfm/extensions/strikethrough.c`의 판정이다.

```c
(delims == 2 || (!(parser->options & CMARK_OPT_STRIKETHROUGH_DOUBLE_TILDE) && delims == 1))
```

- 물결표 2개는 **항상** 취소선이다.
- 물결표 1개는 `CMARK_OPT_STRIKETHROUGH_DOUBLE_TILDE`가 **꺼져 있을 때** 취소선이다. 이 옵션은
  기본값이 꺼짐이다.

즉 **GitHub 자신의 구현도 기본값으로 1개를 허용**하며, 2개만 받도록 **좁히는 공식 옵션이 따로
존재한다.**

`marked` 18.0.9의 정규식도 같은 동작이다.

```text
del: /^(~~?)(?=[^\s~])(...)\1(?=[^~]|$)/
      ^^^^^
      물결표 1개 또는 2개를 캡처해 같은 개수로 닫는다
```

`(?=[^\s~])`가 여는 구분자 뒤에 공백을 금지한다. `1 ~ 3`이 안전한 이유가 이것이다.

### 5.3 그래서 "고치는 것"은 명세 이탈이 아니다

물결표 2개만 취소선으로 보는 것은 **참조 구현이 제공하는 옵션(`STRIKETHROUGH_DOUBLE_TILDE`)과
같은 선택**이고, **명세 본문에 더 가깝다.**

`marked`에는 그 옵션이 없고, 내장 `del` 토크나이저를 덮으려는 시도는 전부 실패했다.

| 시도 | 결과 |
| --- | --- |
| `new Marked({ extensions: [{ name: 'del', ... }] })` | 내장 토크나이저가 그대로 이김 |
| `new Marked({ tokenizer: { del(src) { ... } } })` | 동일 |
| `instance.use({ tokenizer: { del(src) { ... } } })` | 동일 |

대신 **우리 변환기에서 토큰을 후처리하면 확실하다.** `del` 토큰의 `raw`로 구분자 개수를 알 수 있다.

```ts
// markdown-to-adf.ts, renderInlineToken()
case 'del': {
  const del = token as Tokens.Del;
  // 참조 구현의 STRIKETHROUGH_DOUBLE_TILDE 와 같은 선택이다.
  // 물결표 1개는 한국어 범위 표기(`1~3`)와 충돌하므로 취소선으로 보지 않는다.
  if (!del.raw.startsWith('~~')) {
    return [
      { type: 'text', text: '~' },
      ...this.renderInline(del.tokens),
      { type: 'text', text: '~' },
    ];
  }
  return this.withMark(this.renderInline(del.tokens), { type: 'strike' });
}
```

안쪽 서식(`**굵게**` 등)은 `del.tokens`를 그대로 렌더하므로 보존된다.

### 5.4 트레이드오프

| 항목 | 내용 |
| --- | --- |
| 얻는 것 | 한국어 범위 표기가 깨지지 않는다. 글자가 사라지는 손실도 없다 |
| 잃는 것 | 물결표 **1개**로 취소선을 의도한 사용자는 결과가 달라진다 |
| 명세 적합성 | **오히려 명세 본문에 가까워진다.** 참조 구현도 같은 옵션을 제공한다 |
| 위험 | 낮다. 단일 물결표 취소선보다 범위 표기가 훨씬 흔하다 |

**적용을 권한다.**

## 6. 확인하지 못한 것

- `marked` 오버라이드가 왜 안 먹는지 원인을 규명하지 못했다. 후처리 방법이 확실해서 더 파지 않았다.
- **github.com 렌더러의 실제 동작은 확인하지 못했다.** 참조 구현 기본값과 같을 것으로 보이지만 직접 시험하지 않았다.
- Confluence 자체 평문 붙여넣기에서도 같은 현상이 나는지 확인하지 않았다. 이 문서는 우리 변환기
  경로만 다룬다.
