# Inno Extension Semantic Versioning 정책

릴리즈 버전을 결정할 때 적용하는 기준이다. 기본 형식은 `MAJOR.MINOR.PATCH`다.

```text
MAJOR.MINOR.PATCH
  │     │     │
  │     │     └─ 기존 동작을 유지하는 수정
  │     └─────── 하위 호환 기능 추가
  └───────────── 호환되지 않는 변경
```

## 기본 규칙

| 구분 | 적용 조건 | 예시 |
| --- | --- | --- |
| MAJOR | 기존 사용자나 클라이언트가 수정 없이 사용할 수 없는 변경 | `1.4.2 → 2.0.0` |
| MINOR | 하위 호환성을 유지하는 기능 추가 | `1.4.2 → 1.5.0` |
| PATCH | 기존 인터페이스와 기능을 유지하는 수정 | `1.4.2 → 1.4.3` |

버전 증가 시 오른쪽 숫자를 `0`으로 초기화한다.

```text
1.8.4 → 2.0.0
1.5.3 → 1.6.0
1.5.3 → 1.5.4
```

## MAJOR

다음과 같은 Breaking Change에 적용한다.

- 기존 API 또는 공개 인터페이스 삭제
- 요청·응답 구조 변경
- 기존 설정값 제거 또는 의미 변경
- 기존 사용 방식과 호환되지 않는 동작 변경
- 필수 파라미터 추가처럼 기존 클라이언트 수정이 필요한 변경

판단 질문은 다음과 같다.

> 기존 버전 사용자가 새 버전으로 교체했을 때 수정 없이 정상적으로 사용할 수 있는가?

답이 `No`이면 MAJOR 변경이다. 단, `0.x.x` 초기 개발 정책은 아래 별도 항목을 따른다.

## MINOR

하위 호환성을 유지하면서 다음을 추가할 때 적용한다.

- 새로운 기능이나 API
- 새로운 설정 옵션
- 기존 기능을 유지하는 선택 기능
- 호환성을 깨지 않는 선택적 필드

## PATCH

기존 사용 방식을 유지하면서 다음을 변경할 때 적용한다.

- 버그와 예외 처리 수정
- 보안 취약점 수정
- 성능 또는 로그 개선
- 내부 리팩터링
- 문서 및 설정 오류 수정

수정이라는 이름이더라도 기존 사용 방식이 깨지면 PATCH가 아니다.

## 혼합 릴리즈

변경 사항 중 가장 영향도가 큰 등급을 선택한다.

```text
MAJOR > MINOR > PATCH
```

예를 들어 버그 수정, 신규 API, 기존 API 삭제가 한 릴리즈에 함께 있으면 MAJOR를 증가시킨다.

## Pre-release

정식 릴리즈 전 검증 버전은 `-` 뒤에 식별자를 붙인다.

```text
1.2.0-alpha.1
1.2.0-beta.1
1.2.0-rc.1
1.2.0
```

일반 순서는 `alpha → beta → rc → release`다.

- Alpha: 기능이 완성되지 않았거나 변경 가능성이 높음
- Beta: 주요 기능은 완료됐지만 추가 검증이 필요함
- RC: 문제가 없으면 정식 릴리스가 될 후보

정식 릴리즈에서는 pre-release 식별자를 제거한다.

```text
1.5.0-rc.2 → 1.5.0
```

Chrome manifest의 `version`은 SemVer pre-release 문자열을 직접 허용하지 않는다. Inno Extension에서 pre-release를 사용할 때는 `manifest.version_name`, 숫자형 manifest version, package version과 ZIP 이름의 매핑을 먼저 정의하고 검증한다.

## Build Metadata

빌드 정보는 `+` 뒤에 붙일 수 있다.

```text
1.2.3+build.123
1.2.3+20260814
1.2.3-rc.1+sha.a91bc23
```

Build Metadata는 버전 우선순위에 영향을 주지 않는다. Chrome manifest 및 현재 패키징 계약과 호환되는지 별도로 검토한다.

## 초기 개발 버전

공개 인터페이스가 안정화되기 전에는 `0.x.x`를 사용한다.

```text
0.1.0  최초 개발 버전
0.2.0  주요 기능 추가
0.2.1  버그 수정
0.3.0  기능 추가 또는 인터페이스 변경
1.0.0  최초 안정 버전
```

Inno Extension의 `0.x.x` 정책은 다음과 같다.

- 기능 추가: MINOR
- 초기 개발 단계의 호환되지 않는 제품 동작 변경: MINOR
- 기존 동작을 유지하는 수정: PATCH
- `1.0.0` 전환: 실제 사용자가 의존하는 공개 인터페이스와 운영 방식이 안정화됐다고 명시적으로 결정한 시점

## 불변 릴리즈

이미 배포한 버전의 내용은 변경하지 않는다. 동일한 버전을 다시 빌드하거나 태그와 자산을 교체하지 않는다.

```text
1.3.2에서 문제 발견 → 1.3.3 발행
```

하나의 버전 번호는 항상 하나의 동일한 commit과 결과물을 가리켜야 한다.

## 최종 판단 요약

```text
호환성이 깨짐                         → MAJOR
호환성을 유지하면서 기능 추가           → MINOR
기존 동작을 유지하면서 문제만 수정       → PATCH
```

현재 `0.x.x`에서는 호환되지 않는 초기 개발 변경도 MINOR로 다루되, 릴리즈 노트에 영향을 명확히 기록한다.
